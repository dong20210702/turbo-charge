# v76

### Changelog

1.**修复 v75 导致“充电完全不进电”的严重回归**：v75 为保留真实温度观测，把温度伪装缩到只剩 `battery/temp`。实测证明不可行 —— `battery/temp` 是 `bms/temp` 的镜像，BMS 驱动会立刻把真值写回，伪装等于没做。系统重新看到 47℃ 后对充电器做**开/关硬切断**（`ibat` 在 0A 与 6A 之间反复跳），59 分钟电量只从 38% 涨到 48%，之后一小时零增长。现已恢复写遍全部 `power_supply` 温度节点

2.**熔断判断改用电池自身温度，不再用 `wifi_therm`**：这是第二个真凶。`wifi_therm`（主板/WiFi 区）在满速充电叠加重负载时冲到 **54.4℃**，而同期电池只有 47~48℃。旧逻辑拿它和 `FORCE_TEMP_MAX=49` 比，会在电池并不热的时候就把真实温度交还系统，直接触发上面的硬切断。现在改为读 `thermal` 子系统的电池传感器（MTK `mtktsbts*`，本模块从不写入），伪装生效后仍读得到真值

3.**`GUARD_HANDOVER` 新增，默认 0：熔断时只限流、不交还真实温度**：本机实测，系统一旦看见 46℃ 以上的真实电池温度就会反复切断充电器，交还真实温度等于放弃快充。现在熔断只把电流压到 `HIGHEST_TEMP_CURRENT`（6A≈26W），继续保持 28℃ 伪装；日志 `tbat_raw` 列记录真实电池温度供人工核对。需要系统自己接管保护的把这项改 1

4.**`TEMP_MAX` 52℃→58℃、`RECHARGE_TEMP` 45℃→50℃**：`wifi_therm` 峰值 54.4℃，旧阈值 52 会被长期触发；而进限流后它稳定在 49~51℃，出阈值 45 永远达不到，实测 **650 个采样点（54 分钟）卡在 `TEMP-CTRL` 出不来**，平均只有 7.14W

5.**`tbat_raw` 列改为独立观测通道**：取自 `thermal` 子系统的电池传感器，不再依赖会被伪装的 `power_supply` 节点。启动日志会打印实际使用的节点路径，若该机型没有电池温度传感器则给出明确警告（此时这一列失去参考价值）

6.**升级迁移**：`TEMP_MAX=52` 自动升到 58、`RECHARGE_TEMP=45` 升到 50，只对等于旧默认的值生效

# v73

### Changelog

1.**修复温度熔断没有滞回导致的"一半时间在 4W 上爬"**（本次最关键）：进熔断和解除熔断用的是同一个 `FORCE_TEMP_MAX` 阈值，温度在阈值上下抖 1℃ 就会一秒放开大电流、一秒收回小电流。实测日志里 236 个采样点（占充电时间 55%）卡在熔断状态，平均功率只有 4.42W，而不熔断时是 19.75W。现在新增 `GUARD_RECOVER` 作为解除阈值，中间区间保持上一次状态，不再来回切

2.**熔断限流值从 2A 提到 4A**：2A 在 4.2V 电池上只有 8.4W，进入限流区间后充电慢到几乎停滞（实测平均 1.14A）。4A 约 16.8W，既明显降温，又不至于让充电停摆。当前值可在 `option.txt` 的 `HIGHEST_TEMP_CURRENT` 调整

3.**熔断阈值默认值从 45℃ 提到 48℃ 并提供启动告警**：实测该机型 `wifi_therm` 传感器在充电时的常态读数就在 45~47℃，旧阈值正好压在这个区间里，等于全程熔断。启动时会打印完整的温度策略（熔断/解除/限流/温控进出阈值），阈值低于 46℃ 或滞回过小时给出明确警告

4.**温度读数单位自适应**：`/sys/class/thermal/*/temp` 是 0.001℃，`/sys/class/power_supply/*/temp` 是 0.1℃，旧代码一律按 0.001℃ 处理。一旦温度源换到 power_supply，45℃ 会被读成 4.5℃，温度保护等于完全失效。现在按数值量级自动判定（实测该机型 45.0℃ 上报 45000，判定正常）

5.**采样日志新增 `icl_a` 和 `vin_v` 两列**（排查功率天花板的必需数据）：`icl_a` 是输入限流在 AICL 自适应之后真正生效的值，`vin_v` 是充电器实际协商到的电压。模块往里写的是 8A，但有实测机型上电池侧实际只有 5.3A，说明写进去的电流和真正生效的电流不是一回事，此前日志完全看不到这个差值

6.**输出说明**：`icl_a` 与 `vin_v` 采用候选节点探测，MTK 机型优先读 `mtk-master-charger/input_current_limit`，读不到则显示 NA（部分机型 `usb/voltage_now` 恒为 0，属内核未暴露，不是模块读取失败）

# v72

### Changelog

1.**修复电流节点后缀匹配的长度错误**（这是"装了但完全没效果"的真正原因）：`/constant_charge_current_max` 是28个字符却按27去比较、`/fast_charge_current` 是20个字符却按19去比较，差一个字符导致 `strcmp` 首字符是 `c` 对 `/`，这两个最常用的电流节点**从上游版本开始就从来没被识别成功过**，只有 `thermal_input_current` 的长度是对的。也就是说 v70 及之前只有恰好带该节点的机型才真正生效过

2.**适配 MTK（联发科）机型**：新增 `constant_charge_current`、`input_current_limit` 两类节点。MTK 的节点命名与高通完全不同，此前一台天玑8100机型的日志里明确写着"找不到 constant_charge_current_max、fast_charge_current、thermal_input_current"，模块全程没往任何电流节点写过值，表现就是"装了跟没装一样"

3.**按节点自动换算电流单位**：同一台 MTK 机器上，`battery/constant_charge_current` 读出来是 22000000（μA）而 `i2c:mt6375@34:chg/constant_charge_current` 读出来是 2700（mA），两者语义相同但单位差一千倍，用同一个数字写会把电流放大或缩小一千倍

4.**跳过无效节点**：MTK 主从充电架构里，未启用的从充电器节点（`mtk-slave-charger`、`mtk-mst-div-chg` 等）读出来是 -95 这类错误码，路径存在但写进去毫无效果。现在扫描阶段就剔除，不再让"找到了电流文件"的日志骗人

5.**输入限流一并纳入控制**：MTK 机型默认 `input_current_limit` 只有 3A，若充电器协商到 9V 档，3A×9V=27W，正好把功率卡在 27W 上不去。现在随充电电流一起写入

6.新增节点自检报告：电流节点全部不可用时自动生成 `/data/adb/turbo-charge/probe.txt`，逐个列出 `/sys/class/power_supply` 下每个节点的可写性与当前值

7.修复配置值解析的子串误判：旧代码用 `strstr` 做子串匹配，`FORCE_TEMP_MAX=45` 这一行含有子串 `TEMP_MAX=`，被当成在设置 `TEMP_MAX`，又从固定偏移取到 `P_MAX=45`，于是每次启动都报"配置文件中TEMP_MAX的值不是由纯数字组成"，并且 `TEMP_MAX` 的配置值永远不生效。现已改为行首匹配（兼容行首空白）

8.安装脚本同步按"值是否为负"筛选电流节点，与程序内判定保持一致

# v70

6.未充电时一律写回真实温度，避免残留的28℃误导用户

7.默认关闭阶梯式充电（STEP_CHARGING_DISABLED=1），这是“峰值只能维持一会儿就掉到10W”的最常见原因
